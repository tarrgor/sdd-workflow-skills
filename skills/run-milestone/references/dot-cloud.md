# Dot-led cloud coordinator (experimental)

Invoke in the Dot conversation: “Run the active milestone for OWNER/REPO in my named Codex Cloud environment until a project meeting is due.” If a cloud work chat receives this request instead, show that invocation and stop before mutations. No automatic handoff from a worker to its Dot is required or assumed. Codex desktop and Claude Code desktop retain their own adapters.

The Dot applies `run-milestone` Steps 1–4 and the shared issue, feedback, finding, meeting and merge rules. This reference overrides host mechanics only. An issue worker executes one standalone skill in non-interactive mode. The Dot owns dispatch, recovery, user contact, and merge decisions. The worker never starts peer chats, merges its own work, or changes policy. Independent review uses the existing review mechanism, not another issue worker.

## Entry

- Resolve the exact repository, base branch, active milestone and saved cloud environment. Confirm it checks out the intended repository and base, can use an installed or explicitly supplied copy of the SDD skills (including independent review), and can read GitHub and perform specifically authorized writes. Do not assume a local plugin installation, cloud token, command access or inherited permission. Never ask for secrets in chat.
- Before dispatch, confirm the user's scope for cloud chats, independent checkouts, follow-up/retry, authorized GitHub writes, and unattended continuation if requested. Read `parallel` (an integer from 1 to 3) from the existing `.project/RUN-POLICY.md`. Apply the lower of that value and any confirmed host or user limit; never rewrite the policy from a run. If the policy is unavailable or invalid, pause new starts. Re-read it on resume and before admitting more work. If the limit falls below occupancy, let existing units settle without replacements until occupancy is below the new limit. No default-branch merge unless the policy and user mandate permit it. Use default worker model/effort unless approved overrides are both available and compatible.
- Use actual host capabilities: the Dot's `thread_management.create_thread` with the resolved saved environment configuration (current schema), then `read_thread` on the returned chat and `send_message` for an authorized follow-up. Use `list_threads` when recovering an uncertain start. A fresh environment must provide an independent checkout pinned to the approved base and support an isolated issue branch. If it does not, stop; never share a working checkout with the coordinator or another active unit. Native implementation subagents and shell background jobs are not substitutes.
- Keep a normal, current coordinator checkout on the base, or an independently isolated coordinator execution surface that can perform the existing base, merge and test steps. If the Dot cannot execute those steps in the named environment itself, it may dispatch a **separate coordinator-operation task** in that same configuration, within the user's chat and GitHub mandate. Give it only the named operation and its constraints; do not let it dispatch or decide what to merge. Keep merge and full base testing in one exclusive coordinator lane, never two at once. When a PR is ready to merge, stop admitting new units, let admitted units settle, then merge and test the exact new base before admitting more. Do not start an issue worker while a merge or its base checks are pending. If hosted deployment side effects are possible and not authorized, pause before pushing or merging as applicable.
- Establish one active coordinator per repository; if another is known to be active, stop. Journal entries are recovery evidence, not a distributed lock. Do not adopt an existing chat or claim an issue from another run without reconciling that run.

## Durable journal and dispatch

Use append-only GitHub issue comments prefixed `dot-run:` for private repositories, or an approved durable private journal that can be recovered after a Dot restart. Do not put private host, chat or environment identifiers in public issues or reports. If no authorized durable journal is available, do not start. Keep credentials and local paths out of GitHub output in either case.

- Record a stable run and unit token; repository, milestone, issue, operation (`implement`, `feedback` or `merge-test`), approved base, expected paths, environment selector, attempt and state. Add actual chat/turn IDs, PR number, reviewed head, observed outcome and tested base SHA as known. Record the full current state in each journal entry; unknowns are null.
- Before starting or sending a retry, persist the intent and reserve the issue. Use the shared issue labels for implementation/feedback. Include the exact unit token in the title and the attempt token in the brief. Store the admission result and real IDs before another action. An implementation or feedback unit consumes one slot from durable reservation through reconciled terminal outcome; this includes pending or uncertain starts, approval waits and retries in the same chat. Count all occupied slots before every admission. A parked unit releases its slot only after its worker has ended and the outcome is recorded. If journaling fails, pause instead of dispatching or retrying.
- For implementation use `implement-issue`; for existing PR feedback or revalidation use `check-pr-comments` on the same PR. Pass repo, base, issue/PR, non-interactive mode and applicable guardrails; request the unchanged `RESULT:` line. Confirm the worker's checkout and base; preserve other checkouts and unrelated changes.
- Inspect the recorded chat and exact turn. A creation receipt, progress message, disconnection or task listing alone is not a completed result. Use terminal turn status and the result of that turn; if status and result disagree, verify read-only GitHub state plus whether the work has ended before continuing. Recheck running tasks on host-supported completion notifications when available. An active turn that merely has no new messages is not a failed turn.
- If the user requested background continuation, use a supported durable wake or bounded recheck schedule in the Dot, including repository/run identifiers, the same scope, delivery and stop conditions. Reconcile on each wake; do not create overlapping watches. Disable the watch at a user gate, on completion or when canceled. Without durable continuation, disclose the limitation and resume only on a later invocation; never claim an ended Dot turn is still monitoring.

## Recovery and gates

- Before every dispatch and merge, reconcile saved units with the current GitHub states and meeting rules. Inspect a known chat by real ID. If a start response is uncertain, search for the exact unit token and verify repo, issue and brief; a missing/non-unique/inaccessible match pauses the run, not a replacement launch. Before a retry, verify whether its exact attempt was delivered. Unknown `in-progress` reservations stay untouched.
- Consume terminal outcomes once and persist them before releasing the slot. Only a definitive completed failure or missing result permits the shared one retry, in the **same** chat with a new attempt token. Approval or setup waits are not retries. A second failure parks the issue. Follow shared result/label rules; do not invent a host stop capability or claim an inaccessible chat stopped.
- Fill free slots one admission at a time, with shared feedback priority and ready-issue order. Before each admission reconcile new outcomes and apply the shared estimate, dependency and overlap gates. For feedback include the PR’s current changed paths; for implementation use its estimated paths. Compare against all active or pending unit reservations and other open issue PR diffs, including drafts. If paths cannot be bounded or overlap, defer that candidate rather than assuming independence. If published changes reveal overlap, pause new starts and merges for the affected work until the coordinator resolves it and revalidates the exact heads. Apply meeting and pending-finding checks before dispatch and merge. When due, let running units settle without retries; no further starts or merges.
- On success, require the final published PR head to be independently reviewed and tied to a durable receipt (code-free exception as in `implement-issue`); no outstanding high/critical finding. When fixes move the head, re-review the final head within the existing review/fix limit. Verify target repo/base, `Closes #<issue>`, labels, feedback, pending findings, required checks and the current head. No receipt, mismatched head, unavailable checks or disallowed deployment side effect means no merge. Use `merge-pr` with `--match-head-commit` for the reviewed SHA; no administrative or unguarded fallback.
- The worker posts the receipt on the PR and repeats it before `RESULT:`: `DOT-REVIEW: unit=<unit> pr=<n> head=<full-sha> kind=<independent|code-free> unresolved=none`. It posts only after publication and independent verification of that exact head, before setting `verified`. Check the recorded worker turn, PR receipt and GitHub head together; the label alone is not proof. Re-validate stale receipts via the feedback path, keeping the same PR.
- Journal merge intent before executing it; confirm GitHub reports MERGED before branch cleanup or releasing dependent work. A queued merge is not a completed merge. Verify the base commit and run the required full base checks before starting more work. On resume between merge and tests, finish the outstanding base checks first; never merge twice. A broken base goes to the existing critical-finding path.

## Stop, meeting and resume

Complete the SDD run report with the stop reason, landed PRs, pending findings and remaining units; report the blocker if publishing the report is unavailable or outside the mandate. Notify the user in the Dot conversation. At a decision or meeting, prepare the current facts and proposed agenda for `project-meeting`; the user decides in the Dot conversation (voice or text). Do not conduct the decision portion unattended, change specs or auto-resolve findings. Record only confirmed decisions through the existing meeting workflow and authorization. Resume by reconciling the same run, refs and units after approval; never turn a chat reply into a wider mandate.

Before relying on unattended parallel runs, test the selected concurrency on the actual host. Repository maintainers can use `docs/dot-run-milestone-acceptance.md` for the acceptance scenarios.
